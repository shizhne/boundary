# SP 模型设计分析

## 目标与适用范围

将模型解释组织为可用于软件设计说明的素材，使读者能够理解、复核和维护相关实现。简要说明功能目的，随后解释实现结构、算法、状态及其配合关系。

本规范由用户于 2026-09-18 明确要求固化为默认约束；仅在 VE25/SP 项目内生效。项目 `AGENTS.md` 负责自动路由，规则正文以本文件为准。它是已批准的项目工作流默认项，不是工程设计批准结论或全局规则。

- 模型功能与处理逻辑、模块总结、条件/计数/参数/控制信号/接口等解释，默认采用设计视角，无需用户再次指定。
- 完整模块问题建立整体处理链；局部追问只追踪相关输入、判据、状态和下游影响，不重述全模块。
- 用户明确要求功能概览、术语解释/翻译、操作步骤、故障定位或其他交付形式时，遵循当前请求，不强制设计说明目录。回答相关实现原因时仍保持证据准确。
- 本技能不新增工程修改、脚本执行、模型运行、文档归档或知识发布权限，也不要求对已有授权重复确认。

## 设计说明判断与复核

凡涉及设计说明的内容解释、术语、结构、表述、质疑、审阅或修订，先完整读取并应用[判断与复核约定](references/design-explanation-review.md)。这类问题即使没有指定模型路径也触发本技能。

同一可靠上下文中已完整读取且文件未变化时，可复用规则；每次相关答复前仍须执行适用的判断和自检。续接或上下文压缩后，核对约定的读取状态与当前版本；无法可靠确认时重新读取。文件存在、曾经读过或仅有摘要，都不等于本次已经遵循。

约定要求先区分事实错误、说明不足、合理编排选择及证据不足，再说明判断依据，决定解释、保留或修改。每次相关答复查阅约定指定的项目意见记录，核对当前适用的要求、既有判断及替代关系；反馈还用于检查相关位置的同类问题及改写引入的新依赖。采用用户指定的简要、翻译或操作形式时，保留这些判断要求，但不强制展开完整设计目录。

## 组织分析

先明确当前模块的责任边界、输入输出和必要的上下游关系，再沿数据流与控制流展开：

**输入及配置 → 控制判定 → 分支处理 → 状态更新 → 输出封装与消费**

按实际模型选择需要展开的环节。不要将这条主线机械变成固定数量的章节，也不要将模型按块逐个转述。

先组织本节的完整判断关系，再撰写正文。少量有先后或因果关系的分支用连贯文字就地交代条件与动作；共同规则明确后再说明应用如何采用，处理结果明确后再说明编码或字段如何表示。不要先用策略简称留出理解空缺，再靠后文表格、例外说明补齐。发现遗漏时重排相关段落，避免在末尾不断追加补丁。

对每项重要行为，交代以下相互关联的信息：

- 由什么结构或算法实现；
- 依据哪些条件判定；
- 涉及哪些状态及其变化；
- 最终影响哪些数值、有效性、状态或下游行为。

功能规则是实现分析的入口。用文字解释各部分为何需要配合，而不是只在功能描述中插入块名、公式或参数。

## 关键设计信息

### 控制信号与分支

说明选择、表决、使能、复位等控制信号的产生、类型或编码、消费位置及输出影响。区分通道编号、位掩码、布尔标志和数值结果。

涉及条件分支时，按实际条件覆盖主要分支、默认分支和相关边界；跟随控制连线核对，不从块名、排列位置或编号推定逻辑。必要时用表格连接“条件—动作—输出”。

### 状态与历史

涉及计数、延迟、锁存、保持或恢复时，说明状态存储对象、初值、更新条件、保持条件和清除条件。区分：

- 原始有效性、判定后的有效性及异常状态；
- 保持数值、保持来源编号及保持逻辑状态；
- 内部状态复位、计数清零及对外复位通知。

当本次问题涉及触发时刻，核对比较符、计数与比较的先后关系、延迟及复位语义。未证实首拍边界或实际调度时，只描述已确认的计数/条件关系，不擅自断言具体执行拍或秒数。

### 参数与数据结构

先定义参数、符号及控制作用，再说明当前实际绑定、取值、类型和实例差异；不从名称对应关系推定绑定关系。

数据结构按处理链说明提取、转换、保留、覆写及封装关系。单位换算、精度变化和状态字段分流在实际发生位置解释。

举例前声明所用配置、输入和初始状态。例子应解释当前分析对象，不突然转向另一类信号或引入未交代的数值。

## 来源与设计依据

复用已完整读取、未变化且仍可靠的规则与证据；按最小必要范围回到当前权威模型及实际引用文件核对新增事实。当前实现以模型、实际引用的库和参数绑定为依据；需求用于核对意图和对应关系，不能覆盖模型事实。全文检查必须建立逐节覆盖记录，区分已核对、待核对及不在范围内，不能用抽查或文件哈希相同代替全文技术核对。具体证据、差异判定及改写复核方法见判断与复核约定。

区分三类表述：

1. **实现事实：**模型、代码、字典或可复现结果直接支持，保留必要的路径及块/字段/位置锚点。
2. **效果推导：**由实现逻辑推出的作用、限制或权衡，明确这是分析结论。
3. **设计依据：**有适用需求、设计记录或用户明确决定支撑的方案理由。

未知的历史动机、参数选值理由、单位或执行时序标为待确认；不得用通用经验填补成项目事实。静态检查、独立逻辑演算与运行验证分别说明。

## 表达与输出

- 标题采用简洁正式的功能或机制名称，例如“输入数据说明”“配置参数”“分支判定”“状态更新”“输出封装”。不要使用对话式提问或叙事标题。
- 正文承担算法的主要解释，条件、动作与结果应能连续读懂；大量并列配置、分支对照或位编码适合表格，精确计算适合公式或必要伪代码。按信息关系选择形式，不强制每节使用表格，也不将同一规则在文字、表格和伪代码中重复三遍。当前 Markdown 场景避免未验证渲染的 LaTeX 定界符及命令。
- 优先用含义明确的算法对象解释，必要模型字段在首次对应时给出；自定义符号须说明用途。先建立处理含义，再给编码、类型及实现定位，不以变量名、块名或自造策略简称代替算法说明。
- 同一规则尽量集中说明一次，其他部分承接其作用；完整性不等于重复功能行为或堆砌术语。
- 将实现定位集中在必要位置，避免让大量 SID 和块名打断主线。
- 模型问答默认在回答中解释；归档或修改文件沿用当前明确授权，不因调用本技能自动写入说明文档。

## 回答前自检

在本次问题范围内检查，不必输出检查清单：

- 是否沿同一条实现链说明了各部分的分工和配合？
- 关键控制信号是否说明了产生与使用，而不只是最终取值？
- 相关分支、状态初值与清除条件是否闭合？
- 参数和例子是否先定义后使用，数据结构是否能追踪到输出？
- 是否把效果推导写成了未经证实的原始设计意图？
- 读者能否据此复核实现；有无可以删除的重复说明或无关展开？
