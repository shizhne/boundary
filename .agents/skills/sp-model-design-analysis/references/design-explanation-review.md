# 设计说明判断与复核约定

适用范围：VE25/SP 的设计说明相关问答、撰写、审阅与修订，包括局部术语和组织问题。依据：用户于 2026-10-14 要求独立判断质疑、解释修改理由、举一反三，并将本约定用于每次相关回答。本文件为技能的稳定规则来源；过程讨论记录保留在项目任务目录。

## 质疑先核查，再作决定

把用户指出的阅读困难与其推测的技术原因分开。阅读反馈用于定位问题，技术判断仍依据当前来源、正文上下文和已确认的写作目标。

根据核查结果选择处理方式：

- 事实或实现结论错误：纠正，并说明证据及影响。
- 实现正确但对象、条件或依赖未交代：保留行为，补清说明。
- 有合理用途的编排选择：解释用途与代价，结合章节目标决定保留、重排或引用。
- 证据不足：明确已知范围与待核部分，保留已确认事实。

先向用户说明判断及理由，再实施已授权且确有必要的修订。用户质疑本身不使技术推测成立，也不自动扩大写入权限。无法确认原写法有问题时，不为迎合质疑改写事实；已有授权仍按当前任务边界使用，不要求重复批准。

## 意见记录与冲突处理

项目意见历史保存在[设计说明反馈与决策记录](../../../design-document-feedback.md)。每次设计说明相关答复前，查阅其中当前有效的要求及与本次问题有关的条目；已完整读取、未变化且仍可靠的内容可以复用。修改正文前，再核对有关条目的适用范围、处理状态和替代关系。

记录有复用价值的写作要求、纠正点、重要质疑及处理决定，保留登记时间、来源、适用范围、判断依据、实际动作和状态。区分用户明确要求、用户提出的技术推测及助手的核查结论；不把助手的编排判断标为用户批准。仅保存必要摘要，不复制完整聊天。早期意见不能核实原始时间或来源时注明覆盖缺口，不补造历史。

发现前后意见似有冲突时，先判断：

- 适用对象、范围或任务阶段不同：分别应用，说明边界，不视为矛盾。
- 新要求明确替代或细化旧要求：执行当前明确要求，保留旧条目并登记替代关系。
- 用户反馈包含技术推测：先核查实现事实，不把未证实推测作为有效规则。
- 同一范围内的要求确实不兼容，且当前意图无法判断：说明冲突条目、影响、可选处理及建议，请用户决定；只暂停依赖该决定的改动。

不自动折中相互矛盾的条件、参数或事实。编排上的兼容方案可以提出，但不能把未确认的取舍当作用户决定。记录不可读或历史覆盖不全时，说明缺口；依据当前可靠请求继续独立工作，仅暂停确实依赖未知旧决定的修改，不声称已完成历史核对。

重新审视此前处理时，分别检查原结论、实际操作和当前正文。若操作确有错误，在授权范围内落实纠正并记录验证；若需要纠正的是解释或判断，明确说明当前文档是否仍成立、为何保留，以及本轮是否实际改文。不能只承认问题却遗漏必要纠正，也不能为了体现动作而回退合理修改。

## 将反馈用于同类问题

新增分类须有明确依据，检查覆盖范围和实例能否对应处理规则。分类应帮助理解，不能只因名称正式就引入。

术语首次出现时交代对象、含义和作用，区分业务内容、输入有效性、监测状态及事件通知。删除或替换术语后，检查是否又引入未解释的新词。

跨方法对照应服务当前设计问题，检查读者是否已具备比较所需概念、是否已有更合适的统一对照位置。合理对照不因跨越算法类别就必然错误。

概括共性时核对列举应用的适用范围，保留来源判定、历史用途、数值保持及通知输出的差异。

确认一处问题后，在相关章节检查相同或相似的问题类型。只修改证据和上下文支持的问题；不得把单个例子的纠正扩大为全面禁止一种写法，也不为凑数重写清楚内容。

## 先组织处理关系，再选择表达形式

每节先明确读者需要理解的核心机制和必要前提，按实际依赖安排条件、动作、状态及结果。共同规则讲清后再给应用映射；后续解释应承接已经形成的判定结果。不同章节可按数值计算、条件优先或状态变化组织，不把一个示例的段落顺序固化为统一模板。

正文中的规则应在首次展开时具备必要的条件和动作。避免先说“按策略处理”“采用另一分支”，却让读者到后文找策略定义。配置改变规则时，将取值和对应动作放在规则附近；具体实例的绑定值可另列，但不能代替通用分支说明。

用连贯文字说明少量相关分支及因果，用表格支持大量并列信息的查阅，用公式表达精确计算。编码、字段、类型和块位置在读者理解算法后给出，并说明其用途。保留关键实现信息，但不按模型块顺序逐个翻译，也不把同一规则拆成概括、表格和补充说明反复讲述。

发现遗漏时先判断其属于当前规则、应用差异还是实现定位，将它放回相应位置并重读相关段落。新增补充若使前文失去完整含义，应重写该段，不继续在文末叠加解释。

## 实现正确性的核对方法

### 确定来源及覆盖范围

- 当前实现结论以实际读取的模型及活动引用、库定义、字典和参数绑定为根本依据。文档、知识卡和旧答复用于定位；需求用于核对规定的行为，不能反向推定当前模型已经实现。
- 核对保存文件版本及指纹，辨别实际引用、链接覆写、注释块和活动分支。文件未变仅允许复用此前确实读过的证据，不代表未检查部分自动通过。区分模型可配置行为、磁盘保存值与会话／运行值；没有运行证据时不混称“当前运行配置”。
- 局部问题按影响范围追踪；用户要求全文检查时，逐节列出核心判断、依据位置、复核状态和未决项，覆盖定义、公式、分支、参数、历史及接口。记录中明确未核项，不能用抽查、全文搜索或格式检查替代全文技术审查。

### 沿控制与数据传递验证陈述

- 对每个核心规则追踪：输入来自何处、控制条件如何形成、哪个分支被采用、如何更新数值或状态、最终输出及消费位置。由连线和参数确认开关端口、条件优先及默认动作，不从块名、图形排列或函数名称猜测。
- 将输入有效、比较资格、监测状态、参与通道、输出有效和事件通知分别定位；检查内部状态是否真的进入最终输出，是否在封装时替换或终止。不同处理层的保持、默认值和有效性不能相互代替。
- 对历史机制核对保存对象、初值、更新与清除条件、反馈位置、计数与比较顺序。数值保持、来源历史、状态锁存及输出通知分别验证；不把一个 Delay 的存在解释为跨所有分支持续保持。
- 参数追踪到实际绑定、类型、单位、比较符及零／负值边界。涉及调度时间或触发首拍时，缺少默认参数、延迟或执行周期证据就保留待核，不补造精确时序。
- 按规则选择有区分力的边界情形检查，例如有效与一致状态不同、一个与多个输入满足条件、模式切换、门限前后、失效后恢复、历史清除。静态推演只用于检验解释与逻辑是否一致，不能称为模型运行验证。

### 判定需求与实现的关系

先确认同一业务对象、处理层级、输入前提、配置和版本，再比较双方行为。分别记录：同义或经证明等价的表达、配置导致的差别、同一前提下已证实的行为差异、以及对应关系或证据不足的待核项。未经比较不能把它们统称“实现差异”。

公式形式不同先核参数含义、单位和代数关系；当前接口没有旧字段先核上游／下游是否承担该职责。列出能区分双方行为的具体条件，保留需求编号／位置和模型锚点。没有适用构型或变更批准依据时，可以确认“该前提下行为不同”，但不能宣布不符合需求、模型错误或差异已关闭。不得为对齐需求而擅自修改模型或把需求写成当前实现。

### 改写及复核结果

技术核对与阅读核对分别进行。改写前明确需保留的条件、配置、默认动作和状态关系；改写后按来源反向检查，重点防止省略前提、把局部分支扩大为全模型规则、把内部量写成外部字段，以及因移动内容丢失必要定义。表号、引用和来源链接同时复核。

对曾出现误判、配置敏感或含复杂历史的机制，优先安排独立复核；复核者应有当前原始来源，不能仅复述原作者结论。没有独立复核条件时明确检查方式。意见不一致时回到来源解决，不能按人数或语言顺畅程度取舍。

报告实际核对范围、修订位置、证据及剩余不确定性。全文静态检查通过只证明此次检查未留下已知矛盾，不保证不存在所有缺陷，也不替代仿真、工程验收或需求符合性审查。发现缺少证据时收窄结论或标注待核，不以免责声明保留未经支持的确定断言。

## 每次相关答复前的复核

按本次问题范围核对以下关系，不机械扩展到全文：

- 当前结论依据什么，属于事实、效果推导还是编排取舍？
- 读者需要的概念是否已经交代，新概念是否有对象及使用范围？
- 各部分如何承接，是否把并行、串联或可选方法混为同一过程？
- 修改是否解决原问题，并引入新的术语、依赖、范围扩张或技术误解？

实际文档修改分别检查技术内容与阅读顺序。技术检查覆盖受影响的公式、条件、参数、初值、历史状态、接口和来源；阅读检查沿正文顺序确认本段解决的问题、所需概念、处理结果及后续用途。未修改文档的问答只执行适用检查，不宣称完成了文档验证。

约定已读取且未变化时可复用正文，但每次判断与复核仍需执行。若约定不可读，按项目入口的缺失规则报告并处理，不声称已调用或已遵循。

技能和本约定只约束判断、分析及表达，不增加模型运行、工程写入或跨项目发布权限。归档沿用用户当前授权；小幅表述修改按已确认约束不另归档。
