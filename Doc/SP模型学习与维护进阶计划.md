## 1. 学习目标与使用方法

学习主线：**确认工程主线 → 理解总体架构 → 贯通一条信号链 → 掌握状态与时序 → 核对设计依据 → 验证变更。**

最终应能独立回答：

- 一个输入从哪里来，经过哪些处理，最终影响哪些消费者？
- 输入异常后，经过哪些状态和时间条件，输出会怎样变化？
- 这一行为由什么需求、配置和参数决定，设计理由是否有证据？
- 修改某个接口、参数或公共模块，会影响哪些模型和测试？
- 怎样证明预期行为已实现，且已有功能没有被破坏？

参考节奏为 **6 周、每周约 6–8 小时**，仅用于分配学习精力，不是工期或能力保证。基础薄弱时延长相关阶段；以验收结果推进，不按日期强行进入模型修改。

首次接触工作区时，先阅读第 7 章“当前工作区文件与目录导航”，再按阶段推进。

每次学习建议采用“阅读来源 → 自己画图或逐拍推演 → 对照实现 → 记录问题”的顺序。相关笔记可以汇总在本文末尾；后续专题文档如需建立，保存在 `D:\666\VE25\Doc`。本文只创建计划，不预先创建其余材料。

### S2：贯通 CAS 空速链

目标：把一条链看透，而不只是记住模块名称。

概念阅读顺序如下；它不表示实际调度顺序，也不意味着每一路输入经过完全相同的模块：

```text
ADAHRU / FTADC 原始空速
        ↓
数据更新、超时、异常等监控
        ↓
通道比较、选源或表决
        ↓
输出选源、有效性判断、单位转换
        ↓
提供给控制律的空速与有效标志
```

- [ ] 在选定主线中定位输入、处理模型、组包模型及输出；不要混用两套模型的连线作为一条实现链。
- [ ] 记录各关键点的数值、类型、单位、有效性、更新信息和历史状态。
- [ ] 追踪 `AirDataSelect`、`CASVoterType` 的使用位置和条件分支。
- [ ] 对照适用的需求，写出健康、异常、失效和恢复场景的预期行为。
- [ ] 明确现有局部测试台可以观察哪些量，以及尚不能验证哪些主线功能。

建议先完成以下纸面场景表，不填写未经证实的输出值：

| 场景 | 需要回答的问题 |
|---|---|
| 所有通道正常 | 哪些通道参与计算，输出来源与有效性是什么？ |
| 单通道数值偏离 | 比较条件、判定延迟、隔离或选源行为是什么？ |
| 单通道停止更新 | 什么条件触发超时，历史值是否还会影响输出？ |
| 部分或全部通道无效 | 是否保持历史值、给默认值或执行其他策略？有效标志如何处理？ |
| 故障恢复 | 是否需要连续有效、计数回落或复位，何时重新参与输出？ |
| 配置切换 | 输入来源、单位、有效性和退化行为是否发生变化？ |

验收标准：能够把至少一个故障场景从原始输入推演到最终输出，并给出模型位置、参数来源和需求依据；无证据的环节明确标为待确认。

需求阅读线索：`SP_SW_HLR-30`（超时监控）、`-532/-546/-562`（CAS 有效性、复位及计算）、`-695/-696`（输出空速转换与有效性）。使用前仍须核对适用版本。

### S3：掌握公共机制与逐拍运行逻辑

目标：理解状态怎样随时间变化，而不只理解静态公式。

- [ ] 阅读公共库中的 `TimeoutMonitor`、`AbnormalMonitor`、`RangeMonitor`、`CmpMonitor`、`Voter` 和状态设置模块。
- [ ] 记录进入故障、保持故障、退出故障、禁用和复位的条件及优先级。
- [ ] 分清报文更新频率、算法调用周期、仿真步长和时间戳单位。
- [ ] 确认初始化、延迟状态及复位后首拍行为；实际调度证据不足时保留疑问。
- [ ] 为一个监控器绘制“输入—计数—状态—输出”的逐拍表。
- [ ] 将参数分为“脚本声明值、模型/字典引用、实际运行解析值”三栏；缺少运行证据的最后一栏保持待确认。

验收标准：能够解释同一输入为何可能因历史状态不同而得到不同输出；不能仅用“阈值乘以步长”推断实际故障延迟，也不能根据连线位置断言执行顺序。

阅读入口：[SignalProcessingLib.slx](D:/666/VE25/sp/04_Design/common/specification/block_libraries/SignalProcessingLib.slx)、[SpCPT_define.m](D:/666/VE25/sp/04_Design/common/libs/parameters/SpCPT_define.m)、[SpCPF_define.m](D:/666/VE25/sp/04_Design/common/libs/parameters/SpCPF_define.m)。

上表是现存功能分组，不保证每个辅助文件或功能当前完整可用。`project_management/startup/prjSetup.m` 是 SP 启动回调所调用初始化函数的定位入口；`returnToWorkFolder.m` 根据工程目录映射切换工作目录。因此，**工具源码所在的 `tools` 目录不等于 MATLAB 的当前工作目录**。

SP 工程元数据已实际声明相对引用 `../ve25_tool`，`prjDirStruct.m` 也明确映射到该工具目录。迁移工程时，要同时核对引用目标、工具工程定义和依赖路径，不要只搬动一个 `.prj` 文件。

### 7.7 常见文件类型：看到扩展名先判断其角色

以下汇总本工作区已见的文件类型，以及现有流程涉及的代码、缓存类型；具体内容和当前是否存在仍以实际文件为准。

| 类型或模式 | 典型角色 | 常见误解 |
|---|---|---|
| `.prj` | MATLAB 工程入口 | 当作包含全部工程定义的单文件 |
| `.slx` | 模型、模块库或配置/模板模型 | 认为每个 `.slx` 都是可直接运行的业务顶层 |
| `.sltx` | Simulink 模型模板 | 当作正式业务模型 |
| `.sldd` | 数据字典：共享数据、类型、参数或配置等 | 忽略字典引用链、有效配置和同名文件解析 |
| `.slreqx` | 需求集 | 只看编号而不核对需求正文和适用基线 |
| `.slmx`、`~mdl.slmx` | 需求链接等追踪关系的存储文件 | 当作无用临时文件，或认为存在即追踪完整 |
| `.m` | MATLAB 脚本、函数或类；可涉及参数、配置、导入、生成、清理等 | 认为所有 `.m` 都能安全直接执行 |
| `.mlapp` | MATLAB App Designer 应用 | 把应用文件存在等同于功能已验证可用 |
| `.mat` | 参数、工具状态或测试/分析结果等数据 | 只凭扩展名认定是模型输入，或认定是可随意删除的缓存 |
| `.slxc`、`slprj`、`cache` | 仿真/构建相关缓存与产物的常见位置或形式 | 未确认归属、唯一证据和授权就清理 |
| `.c`、`.h` | 代码生成或交付流程处理的代码文件类型 | 从预留目录推定当前已存在完整代码；本次相关输出目录有空目录情况 |
| `.docx`、`.xlsx`、`.xmind` | 需求、计划、指南、检查单、测试点或结果材料 | 文件名含“结果”便认定已批准、适用或通过 |
| `.json`、`.xml` | 工程元数据、检查配置、度量配置等 | 把全部 XML 当模型正文，或把全部 JSON 当可忽略缓存 |
| `.gitkeep` | 保留空目录结构的占位文件 | 当作评审、验证或工具鉴定成果 |
