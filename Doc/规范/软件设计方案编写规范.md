# 软件设计方案编写规范

## 0 目的与适用范围

本文规定全量软件设计方案的组织、编写、审查和维护方法，适用于包含接口、算法、状态、时序、故障处理、模块协同或外部设备交互的软件，也适用于模型驱动开发、代码开发及两者结合的工程。

设计方案面向第一次接触该软件、但具备相应工程基础的读者。文档应同时完成两件事：

1. 解释设计概念从哪里来、为什么采用当前规则；
2. 把接口、判据、状态、时序和模块责任写到能够指导实现与验证的程度。

设计方案不讲解布尔量、数组、枚举、结构体等通用基础知识，也不替代软件需求、接口控制文件、编码规范、安全性分析、详细测试规程或源代码注释。

一份合格的设计方案应使读者在脱离讨论记录和开发者个人记忆后，仍能回答：

- 软件负责什么，责任边界在哪里？
- 软件接收哪些事实，这些事实何时可以使用？
- 各项功能为什么存在，输入怎样一步步形成输出？
- 模块怎样划分，状态和接口由谁产生、由谁消费？
- 初始化、复位、重启、故障、恢复和关键过渡期间会发生什么？
- 哪些设计依赖外部前提，哪些事项仍待确认？
- 应通过哪些场景和不变量验证实现符合设计？

## 1 基本编写原则

### 1.1 全量方案表达唯一的当前设计

全量设计方案是当前有效设计的统一阅读入口，不是讨论纪要、修改清单或历史版本对照表。需求、已批准决策、参考设计、实现和验证资料可以作为编写依据，但进入正文后必须被整理成一套无冲突的当前口径。

正文重点回答“现在怎样设计，以及为什么”。已被替代的名称、接口、状态和算法不得与现行设计并列出现。历史背景只有在能够直接解释现行规则时才简要保留，不展开完整试错过程。

### 1.2 设计、实现和验证必须分开陈述

| 类别 | 应说明的内容 |
|---|---|
| 已确认设计 | 条件、处理、状态、输出和约束 |
| 当前实现 | 已实现的模块、接口和仍为空缺的范围 |
| 已验证结论 | 验证对象、方法、边界和结果 |
| 待确认事项 | 未决问题、影响、临时边界和关闭条件 |

设计已经确认，不表示实现已经完成；实现已经存在，不表示行为已经验证；结构检查或局部测试通过，也不表示系统级安全性已经得到证明。

### 1.3 只写有助于理解、实现和验证的内容

| 应保留 | 通常不写入正文 |
|---|---|
| 软件边界、专用概念和关键设计理由 | 通用编程知识入门 |
| 接口语义、算法、状态、时序和优先级 | 工具操作过程和会话流水 |
| 初始化、保持、锁存、复位和恢复 | 对模型截图逐块翻译 |
| 恶劣场景、保护条件和外部前提 | 没有判据的“提高可靠性”等口号 |
| 模块责任、参数语义和输出作用 | 与本软件无关的外部系统完整设计 |
| 可执行的验证场景和长期不变量 | 为填满模板而设置的空章节 |

外部系统只说明到足以建立软件责任边界和设计前提的程度。软件输出请求、外部系统接受请求和物理动作实际完成是不同事件，不得混为一个结论。

### 1.4 文档必须与运行环境无关

交付正文不得依赖编写者所用计算机的盘符、用户目录、临时目录、工具会话、窗口状态或绝对文件位置。换用另一台计算机、另一位开发人员或另一套合规开发环境后，设计含义应保持不变。

引用工程资产时，应优先使用以下稳定标识：

- 配置项名称和版本；
- 文档编号和章节号；
- 模型、模块、接口或数据类型的正式名称；
- 受配置管理的工程内逻辑标识；
- 需求、设计决定、问题单或验证记录的唯一编号。

本机绝对路径、临时导出位置和工具缓存只能出现在个人工作记录或操作说明中，不得成为设计成立的依据，也不得写入通用设计规则。

### 1.5 易读性是设计质量要求

设计方案应使第一次阅读者能够沿着明确的因果关系理解设计，而不依赖作者口头补充、讨论记录或反复对照实现。易读性不是版式修饰，而是判断设计是否已经被完整表达的一项质量要求。

文档应做到：

1. 先给出软件边界和总体决策链，再展开局部算法；
2. 先定义输入事实和专用概念，再使用这些概念形成判据；
3. 先说明规则的工程目的和成立条件，再给公式、伪代码或真值表；
4. 对复杂关系使用合适的图表，使读者能够直观看到结构、条件、状态或时序；
5. 图表之后用文字说明怎样阅读、能够得出什么设计结论，以及该结论怎样影响下游功能。

同一段内容若仅靠连续文字难以准确表达，作者应主动改用图、表或逐周期示例。反之，单一步骤、单一条件或一句话即可说明的关系，不应为形式完整而强行配图。图表的选择和编制要求见第14章。

## 2 设计依据与口径控制

### 2.1 编写前建立依据清单

| 资料 | 主要用途 | 使用限制 |
|---|---|---|
| 系统和软件需求 | 确定功能、接口、性能和安全约束 | 不得自行扩展需求含义 |
| 已批准的设计决定 | 确定当前设计边界和关键规则 | 不得被旧实现静默覆盖 |
| 专业标准和参考设计 | 建立术语、机理和工程约束 | 参考内容不自动成为本软件设计 |
| 接口与数据定义 | 核对名称、类型、维度、编码和责任 | 数据结构存在不等于业务语义已确认 |
| 模型或代码 | 核对当前实现结构和实际行为 | 实现存在不等于设计正确 |
| 分析、仿真、试验和评审记录 | 支撑理由和验证结论 | 局部证据不得外推为整体结论 |

### 2.2 冲突必须显式处理

资料冲突时，应先判断冲突属于需求、设计、实现还是文字表达。影响功能行为、接口语义、状态优先级、安全边界或验证判据的冲突，不得由作者静默选择。

冲突处理至少应记录：

1. 冲突的多个口径；
2. 对实现、接口和验证的影响；
3. 临时采用的边界；
4. 决策责任方和关闭证据。

### 2.3 每条正文结论都应有依据

正式接口、算法、状态、优先级和参数值应能够追溯到需求、设计决定、接口定义、分析结论或经过确认的工程选择。为解释方便引入的符号和中间概念，可以没有同名实现变量，但必须说明其解释用途。

## 3 全文组织方法

### 3.1 同时按功能边界和依赖关系组织

主章节应以功能责任为基本单位，并按数据和决策的依赖顺序排列。推荐的总体结构为：

```text
文档定位
1 系统目标、软件边界和总体决策链
2 公共概念、接口和执行约定
3 形成基础事实的功能
4 使用基础事实进行决策的功能
5 产生控制、许可或状态输出的功能
6 重要主题专章
7 功能集成和实现结构
8 设计前提、待确认事项和实现边界
9 验证设计与长期不变量
附录：术语、参数、接口或状态速查
```

实际章名应使用真实功能或主题名称。“基础事实”“决策功能”等仅用于说明组织方法，不要求原样成为标题。

### 3.2 功能结构不机械复制实现目录

文档结构表达“软件承担什么责任”，实现目录表达“工程怎样存放和组合”。两者相关，但不必一一对应。

- 一个功能跨越多个实现模块时，应在同一功能章节讲清完整作用链；
- 一个实现模块承担多个独立职责时，应按职责分别说明；
- 模块名称和连接关系应放在相应功能附近；
- 只有跨功能集成本身较复杂时，才另设集成章节。

### 3.3 单项功能按因果关系递进

复杂功能推荐采用以下顺序：

```text
问题与必要场景
→ 核心思路
→ 专用概念和责任边界
→ 输入、输出、参数和内部状态
→ 基础判据与归并规则
→ 确认、保持、状态和优先级
→ 模块实现关系
→ 输出作用、典型场景和验证
```

简单功能可以合并小节，但不得打乱“先定义事实，再说明处理，最后说明结果”的阅读顺序。

### 3.4 一项规则只保留一个主要说明位置

术语定义、接口赋值、完整算法、状态机、参数语义和外部前提都应有唯一的主要说明位置。其他章节只保留理解当前内容所需的摘要和交叉引用。

接口或模块归属改变时，应同步清理旧位置的完整规则，不能以“补充说明”的方式留下两套都像现行设计的口径。

## 4 重要主题专章

### 4.1 为什么需要主题专章

有些设计不属于单一功能，却决定多个功能怎样解释同一事实。若把它们分散在各功能章节，容易产生重复定义、条件遗漏和优先级冲突。此类内容应建立专门章节，先统一规则，再由各功能引用。

### 4.2 哪些内容应独立成章

满足下列任一条件时，应优先考虑设置主题专章：

1. 同一概念被三个或更多功能或模块共同使用；
2. 该主题定义了全软件共同的状态、时间或有效性语义；
3. 该主题跨越软件边界，涉及请求、执行和反馈的责任划分；
4. 该主题包含初始化、锁存、复位、重启或恢复等完整生命周期；
5. 该主题包含多个独立请求源、统一归并和明确优先级；
6. 该主题直接影响控制权限、故障隔离或安全关键输出；
7. 该主题容易与相邻概念混淆，需要统一术语和反例；
8. 该主题具有独立的验证场景和长期不变量。

常见的主题专章包括：

- 数据有效性、新鲜度和最近有效值；
- 初始化、复位、重启和持久化恢复；
- 运行模式、角色或权限管理；
- 控制权移交、输出抑制和恢复；
- 多实例通信、时间对齐和协同决策；
- 健康监控、故障确认和隔离；
- 自检、维护或专项测试流程；
- 公共参数、计时和确认规则。

这些名称只是通用示例。只有主题在实际软件中确实重要时才设置相应章节。

### 4.3 主题专章怎样编写

| 内容 | 应回答的问题 |
|---|---|
| 概念边界 | 该主题表示什么，不表示什么？ |
| 信息来源 | 原始事实由谁提供，何时可用？ |
| 统一规则 | 各功能必须共同遵守哪些判据和优先级？ |
| 状态生命周期 | 怎样进入、保持、退出、复位和恢复？ |
| 作用范围 | 哪些功能生产结果，哪些功能消费结果？ |
| 交互边界 | 与其他主题同时成立时怎样处理？ |
| 风险场景 | 错误解释或错误时序会造成什么后果？ |
| 验证要求 | 哪些场景和不变量能够证明规则得到执行？ |

主题专章不应成为零散规则的收纳区。若内容之间没有共同概念和统一规则，应分别放回对应功能章节。

### 4.4 主题专章与功能章节的分工

主题专章定义共同语义；功能章节说明怎样使用这些语义。例如，有效性专章规定“不可用数据不能作为当前事实”，具体功能章节只需说明哪些输入受该规则约束，以及无可用事实时采取什么业务行为。

不得在每个功能章节重新定义一套有效性、复位、锁存或时间对齐规则。

## 5 概念、术语和总体决策链

### 5.1 专用概念必须先定义后使用

首次使用专用概念时，应说明它表示什么、不表示什么、怎样产生、由谁产生以及被谁使用。

容易混淆的概念应成组区分：

```text
原始观察 ≠ 综合证据 ≠ 最终判定
当前条件 ≠ 已确认状态
请求 ≠ 许可 ≠ 外部执行结果
数据不可用 ≠ 明确的否定证据
暂时不参与 ≠ 永久故障隔离
```

### 5.2 术语应专业、统一且可追溯

同一概念全文只使用一个主名称。信号、模块、数据类型、状态和参数名称应与正式定义一致。为了行文简洁使用简称时，应在首次出现处给出全称或定义。

术语表只收录本软件需要特别解释的词，不收录读者已经掌握的通用编程概念。

### 5.3 总体决策链应先于细节

正文前部应给出从输入事实到最终输出的总体链路：

```text
外部输入
→ 输入规整与可用性处理
→ 基础观察
→ 综合证据
→ 状态或决策
→ 连续确认与提交
→ 软件输出
→ 外部执行及反馈
```

总体链路只表达职责和依赖，不展开模块内部逻辑。后续章节应能够对应到链路中的明确位置。

## 6 接口与数据契约

### 6.1 根接口先说明责任关系

接口章节应先列出根输入和根输出及其生产者、消费者和用途，再按消息或接口对象展开字段。总线名称和数据类型名称不能代替业务说明。

每个有业务意义的输入至少应说明：

| 项目 | 内容 |
|---|---|
| 正式名称 | 与接口定义和实现一致的名称 |
| 类型与维度 | 标量、数组、结构、枚举、位宽和元素顺序 |
| 业务含义 | 表示什么事实，不表示什么事实 |
| 生产者 | 由哪个软件、分区、设备或通信层形成 |
| 初始化 | 初值、首次有效前行为和运行前置条件 |
| 更新与保持 | 新数据、暂未更新、超时和重新获得时怎样处理 |
| 可用性 | 何时可用于业务判定，不可用时数值怎样处理 |
| 时间语义 | 当前周期、上一周期或最近一次有效值 |
| 消费方 | 哪些功能使用该字段及其作用 |

### 6.2 数据值与可用性应分开说明

| 输入状态 | 数据值 | 可用性 | 软件行为 |
|---|---|---|---|
| 新数据到达 | 更新为新值 | 可用 | 按功能规则使用 |
| 暂未更新但未超时 | 保持最后值 | 可用 | 仍可使用 |
| 连续未更新且超时 | 保持最后值 | 不可用 | 不得作为当前事实 |
| 数据重新获得 | 更新为新值 | 可用 | 按规定重新确认 |

可用性编码在状态字或位域中时，也应按相同颗粒度说明。不得仅凭数值保持不变，就推断消息仍然有效。

### 6.3 初始化值不得冒充真实状态

结构清零或枚举初值只规定软件怎样开始，不证明外部系统确实处于该状态。若正常运行前必须取得身份、持久化状态、实际开关位置或其他关键数据，应说明：

1. 由谁提供或装载；
2. 在哪个运行阶段前必须可用；
3. 不可用时是否允许进入正常功能；
4. 失败由本软件处置，还是由平台或系统阻止运行。

### 6.4 编码、编号和数组方向必须无歧义

适用时应定义：

- 枚举符号、实际编码和非法值处理；
- 位定义、保留位和组合更新要求；
- 数组维度、元素顺序、相对位置和全局编号；
- 零基编号与一基索引之间的转换；
- 单位、范围、比例、符号和参考方向；
- 同一消息中必须作为一致快照更新的字段。

合法业务值、初始化值、数据不可用和“没有对象”可能是不同语义，应分别表达。

### 6.5 输出要说明作用边界

每个重要输出应说明初值、更新时机、保持规则、接收方和预期作用。诊断结果、状态、许可、请求和物理反馈应明确区分。

只负责打包或转发输出的模块应引用业务结果的唯一生产者，不得在接口构造处再次实现业务判断。

## 7 功能与算法设计

### 7.1 功能开头先说明必要场景

功能说明应先回答服务对象、输入事实、输出目标和实际作用。若设计由关键场景引出，应说明：

```text
初始状态是什么；
发生了什么输入、故障或时序变化；
直接处理会产生什么具体后果；
因此当前设计增加了什么区分、约束或确认。
```

保留的是现行设计成立的原因，不是完整讨论历史。

### 7.2 先讲判定原则，再给表达式

核心算法至少应说明：

- 需要保证或避免什么；
- 使用哪些可获得事实；
- 为什么这些事实足以支撑判断；
- 哪些反例会使判断失效；
- 缺少事实时是保持、否决还是输出缺省结果；
- 规则依赖哪些外部条件。

自然语言先建立理解，公式、伪代码和真值表随后固定行为。不得用一个长表达式代替设计解释。表达形式的选择及配套文字要求见第14章。

### 7.3 输入、输出、状态和所有权必须明确

每项非平凡功能应列出必要的输入、输出、参数和内部记忆，并说明来源、时间含义、生产者和消费方。

每个业务状态和正式输出应只有一个拥有者。多个模块可以产生独立请求，但最终状态或输出应由一个模块统一归并和赋值。

### 7.4 复杂逻辑应分层命名

```text
基础事实
→ 局部条件
→ 综合条件
→ 确认结果
→ 最终状态或输出
```

中间结果名称应表达业务含义，不使用只反映逻辑门形态的名称。为解释引入的符号不要求模型存在同名信号，但正式实现信号不得与文档含义冲突。

### 7.5 真值表应完整且可解释

真值表应定义输入顺序、条件项、动作、优先级和默认输出。“任意”表示该条件不影响本列结果，不能表示尚未分析。

进入真值表前可以规整输入以降低维度，但必须先说明规整规则。对按上游约束不可达的组合：

1. 说明不可达所依赖的规则；
2. 仍提供确定性输出，避免形成无定义区域；
3. 区分正常业务覆盖和异常输入覆盖；
4. 不因文档说明擅自增加新的故障结论。

对称模块应使用一致的输入顺序、相对索引、条件结构和表格风格。

真值表的标题、适用范围、默认输出、不可达组合和实现追溯等呈现要求见14.4节。本节规定算法内容必须覆盖什么，14.4节规定怎样把这些内容清晰地表达出来。

### 7.6 功能说明必须沿作用链闭合

功能说明不能止于“形成某状态”。应继续说明该状态怎样被下游消费、允许或禁止什么、是否还需确认，以及外部系统预期怎样响应。

```text
输入事实
→ 本地处理
→ 判定或状态
→ 已提交软件输出
→ 外部动作
→ 必要反馈或验证
```

若软件只能覆盖链路的一部分，应明确其终点，不把局部结果描述为系统级保证。

## 8 状态、时序与生命周期

### 8.1 连续确认必须精确到周期边界

每个连续确认或延迟功能都应说明：

- 首个成立周期计为0还是1；
- 第N个连续成立周期是否立即提交；
- 条件失效或候选值变化时计数怎样处理；
- 新值确认期间旧输出保持还是复位；
- 置位和撤销是否采用相同时间规则；
- 软件复位怎样影响计数、待确认值和输出；
- 计数器是否饱和。

存在歧义时，应给出逐周期表：

| 周期 | 输入 | 复位 | 计数 | 输出 | 说明 |
|---:|---|---|---:|---|---|

逐周期表或时序图还应满足14.2节和14.3节的图表说明要求，不能只给出波形或数值而不解释提交边界和工程含义。

### 8.2 有状态逻辑必须说明完整生命周期

| 阶段 | 必须说明的内容 |
|---|---|
| 初始化 | 初态、初值和外部装载依赖 |
| 进入或置位 | 触发条件及生效周期 |
| 保持 | 原因消失后是否继续，保存什么历史 |
| 退出或清除 | 解除条件、权限和优先级 |
| 复位 | 哪些状态被清除，复位周期输出是什么 |
| 重启 | 易失状态丢失后如何恢复必要事实 |
| 异常恢复 | 超时、失败和恢复失败后进入哪里 |

状态机还应覆盖重复启动、中止、超时、失败、恢复、恢复失败和再次进入。没有自动后继的失败状态应定义显式保持终态。

### 8.3 当前值、历史值和提交值必须分清

文档应明确区分当前周期计算值、上一周期已提交值、正在确认的待提交值、最近一次有效外部值和跨重启保存的持久化值。

引入一个周期延迟时，应解释其业务意义，例如建立因果顺序、对齐多个实例的视图或避免同周期反馈，而不能只写“加延迟”。

### 8.4 跨模块时序应贯穿完整链路

凡是输入识别、连续确认、状态提交、请求输出和外部执行分属不同模块，都应给出完整时序场景，检查：

- 多级确认是否叠加成不可接受的延迟；
- 请求撤销是否早于新状态建立；
- 输出恢复是否依赖尚未形成的反馈；
- 是否存在代数环或隐蔽的跨周期循环依赖；
- 复位是否清除了交接仍需使用的历史；
- 过渡期间的空档或重叠是否有明确边界。

### 8.5 同周期优先级必须唯一

复位、故障、抑制、正常更新和恢复可能在同一周期成立。文档应给出统一优先级，并说明优先级作用于状态、计数器还是最终输出。不同章节不得为同一状态定义不同的最高优先级。

## 9 多实例通信与协同决策

本章适用于由多个计算机、处理单元、分区或软件实例共同形成结论的设计。单实例软件没有相关内容时可以省略。

### 9.1 先定义各实例看到的事实

应说明：

- 本地数据使用当前周期还是上一周期已提交值；
- 对端消息对应哪个计算或发送周期；
- 直接数据和转发数据怎样选择；
- 消息可用性和新鲜度由谁判断；
- 数据缺失、明确否定和观察分歧分别表示什么；
- 哪些字段构成同一逻辑快照。

未知或不可获得的证据不得自动解释为明确反证，除非设计已经给出充分条件和安全论证。

### 9.2 时间对齐必须有可说明的基础

不能仅凭“各实例同周期运行”声称数据天然一致。若设计依靠历史值、发送周期、通信调度或消息序号实现时间对齐，应说明其适用范围和最不利偏差。

### 9.3 协同协议必须定义事务边界

涉及步骤推进、结果汇总或共同提交时，应说明：

- 事务标识和步骤标识怎样区分不同轮次；
- 重复消息、旧消息和越步消息怎样处理；
- 谁负责发布步骤，谁负责响应；
- 需要收齐哪些响应才能推进；
- 暂时不一致时允许保持、否决还是进入失败状态；
- 协调者失效后是否允许接替。

### 9.4 本地安全动作与整体协同动作应区分

单个实例根据本地事实执行的保护动作，不应被误写为所有实例已经完成协同。反之，需要多个实例共同成立的条件，也不得因本地条件满足而提前宣布完成。

## 10 实现架构、参数与集成

### 10.1 模块说明到职责边界

每个主要模块应说明功能职责、输入输出、关键状态、唯一产生的业务结果、上下游依赖和当前实现程度。

不必逐个描述逻辑门和连线。只有端口顺序、索引方式、块参数、采样语义或执行顺序会改变功能行为时，才写到具体实现单元。

### 10.2 总线和状态应有唯一赋值点

多个功能可以分别形成局部结果，但正式总线字段和对外状态应由明确的组装或管理模块统一赋值。打包模块只负责结构转换，不重复业务算法。

### 10.3 参数必须能够解释和标定

| 参数 | 业务含义和作用位置 | 类型、单位或计数基准 | 当前值或范围 | 选值理由与验证状态 |
|---|---|---|---|---|

周期参数应给出任务周期、首周期语义和提交边界。开关参数应说明关闭的是观察、确认还是最终作用，避免关闭最终作用的同时丢失必要的诊断结果。

当前实现值不等于已经完成安全性和最不利时序论证。没有依据的数值不得写成正式参数，仅用于解释的数值应标为示例。

### 10.4 集成顺序应表达因果关系

当执行顺序影响结果时，应列出每周期主要处理顺序，说明各模块使用当前值还是历史值。若实际调度与文档叙述不同，应通过明确的数据接口或状态延迟维持相同因果关系。

## 11 设计理由、外部前提与待确认事项

### 11.1 归档结果，也归档成立原因

重要设计不能只保留最终表达式。推荐使用以下结构：

> 在规定场景下，直接处理会造成某个具体问题。因此，本设计区分相关事实，并采用规定的判据、保持、优先级或时序。该做法解决了什么问题，同时依赖哪些前提。

设计理由应靠近对应规则。单独的“设计理由汇总”只适合跨多个功能的共同原则。

### 11.2 关键场景应包含输入、过程和结论

关键场景至少写明：

1. 初始状态和成立假设；
2. 输入、事件或故障变化；
3. 中间证据和状态怎样变化；
4. 哪个功能执行什么动作；
5. 最终软件输出和外部预期反应；
6. 该场景证明哪条规则或暴露什么限制。

允许的短暂过渡不能被写成允许无界等待；可能发生的结果也不能被写成每次必然发生。

### 11.3 外部前提必须靠近作用点

外部前提应说明保证方、被使用的本地规则、前提不满足时失效的结论、退化方案以及所需系统级验证。

存在两种方案时，应明确它们是在设计冻结时二选一，还是软件运行时按条件选择。

### 11.4 待确认事项必须能够关闭

| 项目 | 内容 |
|---|---|
| 未决问题 | 尚未确定的接口、行为、时序或责任 |
| 影响范围 | 受影响的功能、输出和验证结论 |
| 临时边界 | 冻结前允许采用什么，不允许声称什么 |
| 关闭方式 | 责任方以及所需分析、试验或评审证据 |

待确认事项不得被悄悄混入正式算法，也不得因文档重写而自动关闭。

## 12 验证设计与长期不变量

### 12.1 验证场景应从设计规则直接导出

验证章节应按功能或重要主题列出输入条件、事件、预期中间结果、最终输出和判定依据。至少考虑：

- 正常主流程；
- 初始化和不同启动顺序；
- 输入不可用、超时和恢复；
- 条件在确认边界前后变化；
- 状态进入、保持、退出和复位；
- 故障、中止、恢复和恢复失败；
- 多实例消息丢失、延迟、重复和时序错位；
- 参数边界和非法输入；
- 外部前提成立与不成立的边界。

“覆盖全部边界”不能替代具体场景。重要状态机和跨模块时序应给出可执行的初始状态、事件顺序和预期结果。

### 12.2 重要主题应有对应验证集合

每个主题专章至少应有一组直接对应的验证场景。例如，有效性主题应覆盖首次有效、短时未更新、超时和恢复；状态生命周期主题应覆盖进入、保持、复位和重启；协同主题应覆盖数据错位、消息缺失和节点暂时不一致。

### 12.3 长期不变量应贯穿设计和测试

长期不变量描述任何适用运行场景都必须保持的约束，例如：

- 某类输出只能在规定状态下成立；
- 一个请求源不得清除另一个独立请求源；
- 不可用证据不得被解释为明确反证；
- 某状态不得绕过规定的中间状态；
- 每个状态和计数器都有确定的初始化、复位和退出规则。

不变量必须来源于本软件的实际设计，不得把示例直接套用到无关软件。

### 12.4 说明验证证据的边界

结构检查、静态分析、模型编译、仿真、软件测试、硬件在环试验和系统试验证明的范围不同。文档应准确说明使用了哪类证据，以及尚不能证明什么。

## 13 重写、维护与交付检查

### 13.1 重写是重新组织，不是重新设计

重写前应建立内部保留清单，至少包括：

- 正式术语和定义；
- 软件边界和外部前提；
- 接口行为、编码和可用性；
- 算法、真值表、状态和优先级；
- 初始化、复位、重启和恢复；
- 参数语义和模块责任；
- 关键场景、设计理由和长期不变量；
- 当前实现、验证结论和待确认事项。

不得因追求简洁而删除使设计成立的原因，也不得为使章节完整而自行增加状态、接口、参数或优先级。

### 13.2 修改后执行双向覆盖检查

1. **从依据到正文：**每项已确认设计、关键理由和待确认事项是否都有明确位置；
2. **从正文到依据：**每项接口、算法、状态和数值是否都有来源，没有凭空补造。

还应检查是否出现旧名称复活、同一规则多处定义、跨章节矛盾，或将实现状态误写为设计保证。

### 13.3 名称变化必须全局同步

接口、模块、信号、状态或参数重命名后，应同步更新定义、表格、公式、伪代码、图、场景、验证项和附录。功能移动后，应删除原位置的完整重复说明。

### 13.4 归档的含义

“归档”表示最终设计规则、成立原理、选择理由、适用条件、外部前提、证据边界和未关闭问题已经进入当前有效文档。归档不自动表示实现完成、验证通过或正式基线批准。

### 13.5 交付前检查表

#### 13.5.1 内容与结构

- 是否能够脱离讨论记录独立阅读？
- 是否按功能组织并按依赖递进？
- 跨多个功能的重要主题是否独立成章？
- 专用概念是否先定义后使用？
- 每项重要设计是否同时说明结果和原因？

#### 13.5.2 开发可执行性

- 输入是否说明来源、初始化、更新、保持和不可用行为？
- 输出是否说明唯一生产者、消费方和作用边界？
- 模块、状态、参数和执行顺序是否足以指导实现？
- 连续确认是否精确到周期边界？
- 状态、锁存、复位、重启和恢复是否形成完整生命周期？

#### 13.5.3 一致性与安全边界

- 文档、接口、真值表、模型或代码是否使用相同名称和优先级？
- 软件请求、外部执行和反馈是否明确区分？
- 不可用、未知、观察分歧和明确反证是否正确区分？
- 外部前提是否靠近作用点并给出验证要求？
- 允许的空档、重叠和过渡是否有边界？

#### 13.5.4 可移植性

- 是否删除了盘符、用户目录、临时目录和工具会话状态？
- 工程引用是否使用配置受控的稳定标识？
- 换一台计算机后，正文是否仍能完整表达相同设计？

#### 13.5.5 易读性与图表完整性

- 第一次阅读者能否快速找到功能目的、输入、处理、输出和异常行为？
- 三项以上相互关联的条件、状态、步骤或对象，是否已考虑使用合适的图或表降低理解负担？
- 复杂条件组合是否使用真值表或决策表完整表达，并明确默认输出和不可达组合？
- 跨模块数据流、状态转换和关键时序是否采用与关系类型相匹配的图表？
- 每幅图和每张表是否都有标题、适用范围、符号说明和配套文字解读？
- 图表、正文、公式、伪代码和实现名称是否一致，是否不存在相互矛盾的多套口径？

## 14 表达与呈现规则

第1.5节已经把易读性规定为全篇必须遵守的设计质量要求。本章进一步规定文字、图、表、公式和伪代码的选用方法，使各类设计关系能够以最适合审查和实现的形式表达。

### 14.1 段落先给结论

段落按“结论或规则—原因—必要场景”的顺序编写。一个段落表达一个主要意思，重要结论不应隐藏在长段末尾。

避免使用“显然”“肯定安全”“完全一致”“永远不会”等缺少成立条件的绝对表达。

### 14.2 根据关系选择表达形式

| 要表达的关系 | 优先形式 | 配套文字必须说明 |
|---|---|---|
| 软件边界、功能分解和模块责任 | 架构图或层次图 | 每个边界的责任、主要输入输出及图中未包含的范围 |
| 功能责任和数据依赖 | 数据流图或决策链图 | 数据由谁产生、经过什么处理、形成什么结果 |
| 接口字段、对象映射和逐项属性 | 接口表或映射表 | 元素顺序、来源、时间语义、不可用行为和消费方 |
| 多个离散条件共同决定输出 | 真值表或决策表 | 输入定义、优先级、默认输出、不可达组合和最终结论 |
| 状态及转换 | 状态图和状态转换表 | 进入、保持、退出、复位、失败及恢复条件 |
| 多对象交互和消息协调 | 时序图 | 参与者、事件先后、等待条件、超时和失败路径 |
| 连续确认、延迟和逐周期变化 | 时序图或逐周期表 | 首周期计数、提交周期、撤销规则和历史值作用 |
| 数量关系、范围或趋势 | 公式或数据图 | 变量定义、单位、适用范围和工程意义 |

出现下列情况时，应优先使用图或表，而不应只用长段文字描述：

- 一个输入或决定影响三个及以上下游功能；
- 一个功能包含多个状态、分支、参与者或跨周期步骤；
- 多个独立条件共同决定一个输出，且需要检查组合覆盖；
- 本地值、对端值、历史值和提交值存在时间关系；
- 同时存在正常、降级、故障、复位和恢复路径；
- 名称相近的多个信号需要比较其来源、含义和作用点。

图表用于降低理解负担和固定关系，不能代替正文解释。复杂实现截图不能作为算法定义；实现截图只可用于辅助定位，并应另给独立于布局的逻辑说明。简单关系也不为形式统一强行配图。

### 14.3 图和表的编制要求

每幅图和每张表应围绕一个明确问题组织，并至少满足以下要求：

1. 具有能够表明内容和用途的标题；
2. 说明适用功能、运行阶段或边界条件；
3. 图中符号、缩写、颜色、线型、方向和表中“任意”“不可用”等特殊取值均有定义；
4. 名称、方向、元素顺序和优先级与正文及实现保持一致；
5. 必要时给出正常路径、异常路径、默认路径和外部系统边界；
6. 图表前说明为什么需要该图表，图表后说明怎样阅读以及能够得出什么设计结论；
7. 能够追溯到对应接口、算法、状态机、模型模块或验证场景。

一幅图不应同时承担架构、详细逻辑和时序三种目的。连线过多、交叉严重或必须频繁跨图查找时，应按责任层次或处理阶段拆分，并通过清晰的接口名称保持衔接。

优先使用可维护、可版本比较的图表源。无法避免使用图片时，应保证文字清晰、范围完整，并在正文中保存不依赖图片分辨率也能理解的关键结论。

### 14.4 真值表和决策表的专门要求

当输出由多个离散条件共同决定，或者设计需要证明条件组合已经完整覆盖时，应使用真值表或决策表。真值表不只是结果清单，还应使读者能够审查输入规整、优先级和异常覆盖是否正确。

真值表或决策表应明确：

- 输入名称、排列顺序、取值域和时间语义；
- 输入进入表前是否经过规整，以及每项规整的依据；
- 每行条件、输出动作和行间优先级；
- “任意值”的准确含义；
- 没有正常可选结果时的确定性输出；
- 非法输入、数据不可用和不可达组合的处理；
- 不可达组合所依赖的上游规则和仍为其保留确定性输出的原因；
- 与实现中的表项、分支或测试用例之间的对应关系。

不得为了缩短表格而省略可能进入实现的组合，也不得把不可达组合留成未定义区域。若采用通配条件压缩行数，必须保证优先级明确、组合无遗漏，并使读者能够判断任一输入组合最终命中哪一行。

### 14.5 公式和伪代码必须附带文字解读

公式或伪代码按“说明用途—定义变量—给出表达式—解释工程含义—说明输出作用”的顺序出现。不得使用未定义的“条件正常”“满足要求”等占位概念。

伪代码之后必须提供自然语言解读，至少回答：

1. 该段逻辑试图判断或控制什么；
2. 各条件分别提供什么证据，为什么要这样组合；
3. 输入不可用、条件分歧或非法值时采取什么行为；
4. 使用的是当前周期值、上一周期值还是已确认值；
5. 输出由哪个功能消费，会允许、禁止或触发什么；
6. 在最容易误解的边界场景中，逻辑将怎样逐步运行。

读者不应仅靠逐字符解析伪代码来推断上述含义。伪代码用于固定规则，文字解读用于建立工程理解，两者缺一不可。

### 14.6 保持必要的教学性

教学性不等于从基础语法讲起。应重点解释：

- 为什么需要当前概念；
- 相邻概念为什么不能合并；
- 输入怎样逐层形成输出；
- 哪些边界场景最容易误解；
- 当前设计解决了什么问题，又保留了什么限制。

## 附录A 单项功能编写模板

以下模板用于检查复杂功能的完整性。简单功能可以合并小节，没有实际内容的可选部分应省略。

```markdown
## X [功能名称]

### X.1 功能目的与必要场景

说明服务对象、输入事实、输出目标和需要解决的具体问题。

### X.2 核心思路与责任边界

解释判定原则、选择理由以及软件与外部系统的责任分界。

### X.3 接口、参数和内部状态

列出输入、输出、参数和历史状态，说明来源、初值、时间含义和消费方。

### X.4 判定、归并和确认逻辑

先说明基础事实和反例，再给公式、伪代码或真值表。

### X.5 状态、优先级和时序

说明进入、保持、退出、复位、重启、恢复和同周期优先级。

### X.6 实现结构与输出作用

说明模块职责、唯一赋值点和结果怎样进入后续作用链。

### X.7 场景、验证和待确认事项

给出正常、边界、故障和恢复场景，说明外部前提和当前证据边界。
```

## 附录B 重要主题专章模板

```markdown
## X [重要主题名称]

### X.1 主题定义与必要性

### X.2 共同概念和信息来源

给出所有相关功能共同遵守的判据、归并规则和优先级。

### X.4 生命周期与时序

说明初始化、进入、保持、退出、复位、重启和恢复。

### X.5 功能使用关系

列出生产者、消费者、作用范围和跨主题交互。

### X.6 关键场景、外部前提和验证

说明风险场景、成立条件、长期不变量和验证集合。
```

## 附录C 推荐编写流程

1. 明确软件边界、读者和文档范围；
2. 建立设计依据及冲突清单；
3. 画出从输入事实到最终输出的总体决策链；
4. 识别功能边界和跨功能的重要主题；
5. 先写公共概念、接口和重要主题，再写各功能算法；
6. 补齐状态生命周期、跨模块时序和外部前提；
7. 按实现结构核对模块职责、参数和唯一赋值点；
8. 从规则导出验证场景和长期不变量；
9. 检查复杂关系是否已使用合适的图、真值表、状态图、时序图或映射表表达，并补齐配套文字解读；
10. 执行依据到正文、正文到依据的双向覆盖检查；
11. 检查术语一致性、易读性、环境无关性和交付边界。
