- 版本：v2.0
- 日期：2026-07-31

> [!summary]
> 本方案把“自生长”定义为：在受控来源、明确问题、证据链、人工审核和定期质检的驱动下，知识以可追溯的增量持续积累。  
> 项目事实留在项目；Codex 负责提取、链接、索引、候选综合和机械维护；人负责来源选择、工程判断、跨项目放行以及 L2/L3 升格。

## 1. 结论与核心决策

当前工作区不适合照搬“LLM 完全拥有 Wiki”的个人知识库模式，应采用“可审计的知识编译系统”：

1. 原始来源不可被知识维护流程修改。
2. Obsidian 是综合知识库、知识运营台和工作型 Wiki，不是项目事实的唯一来源。
3. V500E 与 volant_XJ 的项目事实分别由各自项目知识库保管。
4. 通用 L0–L3 工程知识正文统一由 Obsidian 保管；成熟度不改变知识所有权。
5. Codex 可以维护 L0/L1 候选层；L1→L2、L2→L3 必须人工批准。
6. 每次任务只沉淀“知识增量”，不把完整聊天、原始日志或整包资料塞进 Vault。
7. 知识增长以证据覆盖率、验证率和复用率衡量，不以文件数量、字数或图谱密度衡量。
8. AI_Global_Assistant 只定义“Codex 应怎样工作”，并提供知识路由；它不保存领域知识正文。
9. 项目经验采用半自动流入：Codex 负责发现、分类、抽象和生成候选，用户只处理关键工程审批。
10. 失效知识先退出默认检索，再修订、替代或归档；物理删除是有恢复保障的人审例外。

一句话机制：

> 来源不搬家，事实不串库，综合可回溯，候选要审核，验证后升格，过期不删除但退出默认检索。

## 2. 对 Karpathy 原始思路的准确理解

用户所说的“卡帕西自生长知识库理论”，最可能对应 Andrej Karpathy 在 2026 年 4 月发布的 LLM Knowledge Bases 长帖与 LLM Wiki Gist。

需要先澄清：Karpathy 将其称为一种 pattern 和 idea file，并未把它定义为经过论文验证的正式理论。“自生长”是对其 persistent、compounding、keeps getting richer 等描述的概括。

一手来源：

- [Karpathy：LLM Knowledge Bases 原帖](https://x.com/karpathy/status/2039805659525644595)
- [Karpathy：LLM Wiki Gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)
- [LLM Wiki 固定版本原文](https://gist.githubusercontent.com/karpathy/442a6bf555914893e9891c11519de94f/raw/ac46de1ad27f92b28ac95459c782c07f6b8c964a/llm-wiki.md)

### 2.1 Karpathy 明确提出的部分

| 原始构件        | 含义                            |
| ----------- | ----------------------------- |
| Raw sources | 人工筛选、保持不可变的原始来源，是事实依据         |
| Wiki        | LLM 增量维护的互联 Markdown 页面，是派生知识 |
| Schema      | AGENTS.md 等规则文件，规定结构、命名和工作流   |
| Ingest      | 读取新来源并更新摘要、实体页、概念页、索引和日志      |
| Query       | 基于已有 Wiki 综合回答；高价值回答可以回写为新知识  |
| Lint        | 检查矛盾、陈旧声明、孤儿页、断链、缺失概念和数据缺口    |
| index.md    | 面向内容的导航目录                     |
| log.md      | 追加式时间线，记录 ingest、query 和 lint |

Karpathy 的人机分工是：人选择来源、提出好问题并理解意义；LLM 承担摘要、归档、交叉引用和维护工作。

### 2.2 本方案增加的工程化约束

以下内容是针对当前飞控/Simulink/工程知识环境的加固，不是 Karpathy 原话：

- 增加 L0–L3 成熟度、人审门槛和适用范围。
- 增加项目隔离、脱敏和跨项目迁移闸门。
- 增加来源版本、哈希、精确锚点、失效条件和验证记录。
- 禁止将 LLM 摘要作为另一条结论的唯一证据，避免自引用污染。
- 增加 stale、conflicted 等健康标记，让过期或冲突知识退出默认使用。
- 让 LLM 拥有候选层的维护工作，人拥有确认层和验证层的发布权。

本方案不把该模式理解为“RAG 已失效”，也不理解为“AI 会自动产生真理”。小规模先依赖 index、全文搜索和明确链接；只有实际检索开始失效时，再考虑本地混合搜索。

系统不是单向“导入”，而是四个闭环：

1. 来源闭环：来源登记 → 单源提取 → 证据核对。
2. 综合闭环：去重 → 跨源综合 → 假设和边界检查。
3. 项目闭环：项目知识更新 → 项目内验证 → 项目 KB 同步。
4. 跨项目闭环：抽象脱敏 → 目标项目验证 → 人工确认 → 通用知识升格。

## 5. 知识分类模型

### 5.1 页面类型

| type | 用途 | 是否可直接作为工程依据 |
|---|---|---|
| source | 来源卡：记录路径、版本、作者、权限和来源类型 | 只能定位原始依据 |
| evidence | 单源证据卡：忠实提取原文或源文件信息 | 可作为引用入口，但不能替代原始来源 |
| concept | 概念页：统一术语、定义和相互关系 | 取决于其中各声明的成熟度 |
| method | 方法页：问题、输入输出、步骤、假设、验证与失效边界 | L2/L3 且来源完整时可以使用 |
| decision | 决策记录：背景、决定、理由、备选和验证计划 | 仅在标明的项目与版本范围内有效 |
| question | 待确认问题、矛盾或证据缺口 | 不可作为结论 |
| moc | 主题地图或索引 | 只负责导航 |
| transfer | V500E/volant_XJ 跨项目迁移申请和审核记录 | 审核通过前不可在目标项目直接采用 |
| retrospective | 任务复盘和工作流候选 | 仅方法性内容可进一步升格 |

### 5.2 四个正交维度

不要把成熟度、审核动作、适用范围和敏感级别混为一个字段。

| 维度 | 建议值 | 回答的问题 |
|---|---|---|
| maturity | L0 / L1 / L2 / L3 | 证据和验证成熟到什么程度 |
| review_status | inbox / candidate / needs_redaction / pending_review / approved / rejected / deprecated | 当前处于什么审核动作 |
| scope | personal / project:V500E / project:volant_XJ / cross-project / global | 可以在哪里使用 |
| sensitivity | public / internal / project_confidential / restricted | 哪些主体或服务可以接触 |

另设迁移策略 `cross_project_policy: allowed / conditional / prohibited`，用于区分“当前仅在项目内使用”与“明确禁止跨项目迁移”；它不是成熟度、审核状态、适用范围或敏感级别的替代字段。

`record_role` 只允许 `canonical / pointer / derived_view`。pointer 和 derived_view 只用于迁移追踪或导航，不是独立工程证据。

附加健康标记 flags：

- stale：来源版本已变化或超过复查期限。
- conflicted：存在无法合并的来源或项目结论冲突。
- superseded：已有替代条目。

内容变化后把 `review_status` 置为 `pending_review`；需要脱敏时置为 `needs_redaction`。这两者不是健康标记。`restricted` 只属于 `sensitivity`，不能再作为 scope 或 flag 使用。

工程结论进入默认检索与回答的唯一判据为：

~~~text
record_role = canonical
AND maturity ∈ {L2, L3}
AND review_status = approved
AND scope 与当前任务匹配
AND sensitivity 允许当前使用者、目标位置和工具接触
AND flags 不含 stale / conflicted / superseded
AND review_due 已填写且尚未到期
~~~

L0/L1、待审核、过期、冲突和已替代内容仍可用于发现问题与追踪证据，但必须显式标注，不能作为默认工程结论。

### 5.3 成熟度沿用现有规则

- L0 灵感：捕获的线索，只能作为候选线索。
- L1 待确认：结构完整且已有初步来源，但不可作为工程定论。
- L2 已确认：人工确认了来源、范围、版本和内容，可在限定范围内使用。
- L3 已验证：满足对应风险等级的验证门槛，并由责任人批准。

L3 采用风险分层：

- 低/中风险的通用工作流、模板和非工程性方法，可由三个独立任务复用，或两个独立场景验证后申请 L3。
- 高风险声明包括控制律、接口、参数、飞行试验结论、安全约束和模型集成行为。此类知识升 L3 必须同时具备可复现验证产物、明确版本与工况、责任人确认；多项目或多任务复用只能作为附加证据，不能替代工程验证。

L3 不等于永远正确。来源版本改变、验证失败或适用边界变化时，应标记 stale 或 conflicted 并退出默认检索。

## 6. 核心元数据与按需生命周期字段

以下 YAML 是已批准的完整参考 schema，不表示每个页面在所有状态下都必须填写全部字段：

- 持久化页面至少维护身份、类型、成熟度、审核状态、范围、敏感级别、风险、来源、唯一正文角色、健康标记和时间字段。
- `cross_project_policy` 只在项目或跨项目条目中按需使用。
- `superseded_by/status_reason/invalidated_at/invalidated_by/decision_ref/review_owner` 是生命周期字段；发生待复核、冲突、失效、替代或废弃时必须补齐，模板预留空字段不等于事件已发生。
- `approvals` 在升格或人工裁决时追加，`gate_records` 只在跨项目闸门等需要逐关审计的页面中追加。
- L0/L1 可暂不填写 `review_due`；可作为默认工程结论的 L2/L3 页面在批准时必须按风险等级填写 `last_verified`、`review_owner` 和日期格式的 `review_due`。

source_kind 建议值：

- primary：原始代码、模型、数据、正式文档、原始论文或用户明确决定。
- secondary：综述、外部解读、项目报告中的二次总结。
- derived：由多个来源推导的知识。
- ai-generated：LLM 生成且尚未核验的内容。

关键规则：ai-generated 和 derived 页面不能互相循环引用后伪装成 primary 证据。

### 6.1 正文固定分层

工程类知识页默认采用：

1. 一句话结论
2. 关键假设和适用边界
3. 已确认事实
4. 推导结果
5. 合理推测
6. 待确认问题
7. 验证记录
8. 来源与精确锚点
9. 变更与失效记录

高风险声明应额外记录：

- 声明 ID 和声明类别。
- 来源文件、版本、提交或数据时间戳。
- 章节、公式、图表、变量、脚本或模型路径等精确锚点。
- 适用项目、软件版本、飞行构型和工况。
- 推导脚本、输入、输出与验证人。
- 失效条件和复查触发器。

### 6.2 审批与迁移闸门记录

单个 `reviewer` 字段不足以审计升格和 G0–G5。需要批准的页面使用追加式记录：

~~~yaml
approvals:
  - action: promote_L1_to_L2
    reviewer:
    reviewed_at:
    decision: approved
    artifacts: []
    reason:
gate_records:
  - gate: G0
    project: V500E
    status: pending
    reviewer:
    decided_at:
    artifacts: []
    reason:
    canonical_record:
~~~

批准记录不得静默覆盖；驳回、撤回和重新批准都追加新记录。`artifacts` 必须指向可复核产物，不能只写“已验证”。

## 7. 知识的蒸馏与提纯机制

### 7.1 不是“摘要”，而是三阶段编译

#### 阶段 A：单源提取

- 一张证据卡只对应一个来源。
- 忠实记录来源说明了什么、没有说明什么。
- 区分原文事实、作者推导、读者推测和工程建议。
- 飞控文献按三遍阅读法执行：先判断价值，再提取方法，最后评估复现与工程适用性。
- 公式、物理量、参考位置、坐标系、方向、总量/分量/增量必须一致。

#### 阶段 B：跨源蒸馏

- 先查 canonical 页面，避免为同一概念重复建页。
- 将相同结论合并为证据集合，不重复堆放摘要。
- 将不同构型、版本、工况的结论并列，不强行平均。
- 建立概念、方法、假设、验证和失败模式之间的双链。
- 输出的是“知识增量”，不是整篇重写。

#### 阶段 C：工程提纯

只有同时满足以下条件的内容才保留为候选：

1. 有新意：不是已有页面的同义复述。
2. 可复用：未来任务确实可能再次用到。
3. 有证据：能够定位到原始来源或可复现验证。
4. 范围明确：知道适用项目、版本、构型和失效条件。
5. 非敏感：没有把项目专用参数、接口、日志或受控资料带入错误层级。

不满足条件的处理：

- 只是临时上下文：不入库。
- 只是原文摘录：留在 evidence，不升格为 method。
- 来源不足：转为 question。
- 内容冲突：标记 conflicted，保留双方证据。
- 强项目绑定：留在对应项目 KB。
- 重复内容：链接已有 canonical 页面，不新建正文。

### 7.2 禁止知识通胀

以下结果属于合法的“无知识增量”：

- 查询只重复已有结论。
- 当前证据不足以形成新判断。
- 结果只对一次性调试有用。
- 内容无法脱敏或没有跨任务复用价值。
- 新来源没有改变现有综合结论。

系统允许在 log.md 中记录 no-change，而不是强行生成一篇新笔记。

## 8. 四个标准操作

### 8.1 Ingest：摄入

1. 检查来源权限、类型和项目归属。
2. 排除缓存、临时文件、重复副本和未知来源。
3. 为来源建立 source 卡，保存路径、版本、哈希或时间戳。
4. 采用单源方式生成 evidence 卡。
5. 查 index 和 canonical 页面，判断新建、更新、冲突或无变化。
6. 有语义增量时记录 `delta_operation`：
   - create
   - update
   - contradict
   - supersede
   - question
7. 执行 `ΔK route`：`no-change / project-only / obs-candidate / global-config-candidate`；无增量使用 `no-change`，不伪造 `delta_operation`。
8. 按写入授权规则决定直接创建或先审 diff。
9. 更新获准页面、index.md 和追加式 log.md。
10. 执行一次局部 lint。

默认一次只摄入一个来源。批量摄入必须先提交来源清单、分类和抽样审核方案。

明确授权的单源摄入任务，可以直接新建 L0/L1 候选，并执行 index、log、反向链接等机械更新。修改已有正文的语义、批量写入、合并、重命名、删除、升格、项目 canonical 变更和跨项目发布，必须先给出 diff 或变更清单并取得针对该动作的批准。用户在当前任务中已经给出的明确授权视为有效批准，不重复询问。

项目任务结束时采用四路由，用户不需要手工复制 Markdown、选择目录或维护 YAML：

| 路由 | 内容 | 处理位置 |
|---|---|---|
| `no-change` | 一次性调试、重复信息、证据不足 | 不入库；必要时只在 log 记录 |
| `project-only` | 参数、接口、模型结构、项目版本结论 | 只更新来源项目知识库 |
| `obs-candidate` | 可复用方法、检查清单、失败模式、验证框架 | 先登记项目指针事件；经 G1 受理、G2 抽象脱敏后建立 L1 草案，并继续审核 |
| `global-config-candidate` | Codex 工作规范、Prompt、Skill 或审核机制改进 | 交给 AI_Global_Assistant 的配置候选流程 |

默认模式为“半自动知识编译”：Codex 自动完成发现、查重、来源定位、抽象脱敏草案和 lint；在当前任务或常设规则已明确授权相应目标目录写入时，可以进一步创建 L0/L1 候选并机械更新索引。用户仍批准项目事实、脱敏放行、跨项目发布、L1→L2、L2→L3、冲突裁决、语义合并和删除。没有任务或已配置的自动化时，Codex 不会后台持续监控项目目录。

### 8.2 Query：查询与回写

1. 先读 index，再读相关 Wiki 页面，最后回到必要的原始来源。
2. 回答中引用 canonical 页面和原始证据。
3. 回答后先判断 `ΔK route`；有可复用增量时再记录 `delta_operation`。
4. 有价值的回答先进入 `review_status=candidate`，不自动变成 `approved` 或 L2。
5. 无新增知识时不写页面。

### 8.3 Lint：知识健康检查

Lint 默认先只读报告，不自动重写语义内容。

检查项：

- 断链、孤儿页、重复标题和重复 canonical ID。
- L2/L3 页面缺少来源、版本、验证或适用边界。
- AI 页面互相引用形成证据闭环。
- 来源发生变化但依赖页面未标 stale。
- 项目事实泄漏到 cross-project 或 global。
- 术语、符号、坐标系和单位不一致。
- 新来源与旧结论矛盾但未标 conflicted。
- 已废弃页面仍被 index 当作当前知识。
- review_due 到期。

### 8.4 Promote：审核与升格

- L0→L1：补齐来源、范围、类型、失效条件并去重。
- L1→L2：人工确认事实准确、引用完整、范围正确，并按风险等级填写 `last_verified`、`review_owner` 与 `review_due`。
- L2→L3：按风险分层执行；高风险工程声明必须有可复现验证产物、明确版本/工况和责任人批准，复用次数只作附加证据。
- project→cross-project：先完成抽象、脱敏和目标项目适用性验证。
- cross-project→global：需要人工确认适用前提、不适用场景和验证记录。

## 10. 知识失效、隔离与退出机制

知识库的“纯洁性”定义为：默认检索只呈现当前有效知识；过时、冲突、被替代或被推翻的内容退出日常使用，同时保留失效原因、证据和替代路径，防止旧错误再次出现。

### 10.1 三层健康区

- 活动知识层：满足第 5.2 节全部条件的 L2/L3。
- 审核隔离层：`pending_review`、`stale`、`conflicted` 或复核到期的条目。
- 历史归档层：`deprecated`、`superseded`、驳回记录和迁移/裁决记录。

### 10.2 失效触发器与处置

来源版本、提交、项目基线、构型、接口、模型或参数体系变化，新仿真/试验否定旧结论，权威来源更新，用户明确纠正，来源断开或出现高可信冲突，都会立即触发影响分析，不等待 `review_due`。

| 情况 | 状态动作 | 后续动作 |
|---|---|---|
| 来源变化或复核到期 | `pending_review + stale` | 退出默认检索，核对下游依赖 |
| 新证据冲突 | `pending_review + conflicted` | 保留双方证据，等待人工裁决 |
| 新知识明确替代旧知识 | 旧页 `deprecated + superseded` | 填写 `superseded_by` 并链接新页 |
| 旧知识被推翻且无替代 | `deprecated` | 记录推翻证据、原因和责任人 |
| 适用工况不同 | 保持两个条目并收紧 scope/边界 | 不强行判定一个真、一个假 |
| 从未生效的低质量候选 | `rejected` | 不进入有效索引，保留审核理由 |

`rejected` 只用于从未获准生效的候选；曾经有效而后来失效的知识必须使用 `deprecated`，不能抹去其曾经生效的历史。

### 10.3 失效处理顺序

1. 若触发源属于项目，先由对应 kb-sync 按项目现有格式标记旧结论，记录状态、原因、时间、触发来源和替代路径，并让项目默认索引只指向当前结论；项目 KB 不被强制套用 Obsidian YAML。
2. 记录项目出口事件或 Obsidian 触发来源、发现时间和影响范围。
3. 先置 `pending_review` 并添加健康标记，使 Obsidian 条目退出默认检索。
4. 沿 `source_paths`、`derived_from`、反向链接和 `superseded_by` 检查下游影响。
5. 生成人工审核包，决定恢复、修订、替代、废弃或删除。
6. 更新项目/Obsidian 有效索引、健康视图和追加式 `log.md`。
7. 执行查询回归，确认旧结论不再作为默认答案。

若一页只有部分声明失效，页面先整体进入 `pending_review`；修订后再恢复仍成立部分。高风险声明应使用声明 ID，经常独立变化的结论应拆成较小页面，不允许长期在一个 approved 页面中混放有效和失效结论。

### 10.4 复核周期

- 高风险工程知识：90 天或每次项目基线变化，取先到者。
- 中风险知识：180 天。
- 低风险通用方法：365 天。
- 不可变的原始证据卡：以事件触发复核为主。

### 10.5 归档与物理删除闸门

先逻辑退出，后考虑移动；不为目录整齐频繁移动文件。物理删除只适用于缓存、空候选、无独立价值的完全重复副本、可再生成视图或误摄入敏感内容，并必须同时满足：

1. 已验证 Git、快照或其他可恢复版本历史。
2. 没有有效入链和下游依赖，或依赖已迁移。
3. 替代页面已经生效。
4. 经过至少 90 天或一个项目发布周期的观察期，取更长者。
5. 已向用户列出准确路径、理由和恢复方式，并获得明确批准。
6. 删除后完成断链、索引和查询回归检查。

- 形成一个跨项目候选。
- 至少完成一次目标项目验证后，才考虑 L2。

第二个可选试点是“控制分配可行性与约束验证流程”。

| 操作 | Codex 可自动执行 | 需要人工批准 |

| 提议新页或合并页 | 是 | 合并、重命名、删除需要 |

| L1→L2、L2→L3 | 否 | 必须 |
| 修改项目 canonical 结论 | 否 | 必须，并走项目 kb-sync |
| 判定完成脱敏并跨项目发布 | 否 | 必须 |
| 修改 AGENTS.md、Schema 或自动化规则 | 否 | 必须 |
| 向外部模型、插件、向量库或同步服务发送内容 | 否 | 必须明确授权 |

“人工批准”可以由用户在当前任务中明确给出；已经覆盖具体范围与动作时，不重复请求。它不能从“请阅读/分析”推定为写入授权，也不能从 V500E 的授权外推到 volant_XJ。

## 14. index.md 与 log.md

### 14.1 index.md 与 Base

`index.md` 负责经过人工策划的入口、用途和主题关系；Base 负责机器汇总元数据。两者共同提供：

- index 中的页面链接或 canonical 路径与一句话用途。
- Base 中的 type、maturity、scope、最后核验时间、主要来源和 stale/conflicted 标记。
- `当前有效工程知识.base` 只展示可作为默认工程知识候选的 concept/method；`当前有效.base` 展示所有当前有效记录，避免把来源卡、目录或运营记录误当作工程结论。

每次有效 ingest、promote、deprecate 后更新 index；Base 通过字段自动刷新。

### 14.2 log.md

log 只追加，不静默改写历史：

~~~text
## [2026-07-31] ingest | 条目 ID | 来源 | 影响页面 | 审核状态 | 结果
## [2026-07-31] query-writeback | 条目 ID | 问题 | delta_route / delta_operation | 审核状态 | 结果
## [2026-07-31] lint | 范围 | 问题数量 | 处理结果
## [2026-07-31] promote | 条目 ID | L1→L2 | 验证依据 | 确认人
~~~

log 只记录元数据和摘要，不记录完整聊天、原始日志内容或敏感项目事实。

## 15. 运行节奏

| 节奏 | 动作 |
|---|---|
| 每次来源摄入 | 单源提取、ΔK route、delta_operation、局部审核、index/log 更新 |
| 每次重要任务结束 | 执行四路由；项目事件增量进入半自动编译，允许 no-change |
| 每周 | 清理 inbox、去重、检查断链、无来源声明、stale、conflicted 和事件积压 |
| 每月 | 复核 L1 候选、处理跨项目迁移、检查 review_due、替代关系和废弃页 |
| 每季度或里程碑 | 评估 L2→L3、全局规则升格、Schema 是否需要调整 |
| 来源版本变化时 | 将下游页面置为 `review_status=pending_review`，必要时同时标记 stale |

Schema 和 AGENTS.md 的修改频率应低于普通知识页，且每次必须人工审查，因为它们会影响后续所有知识写入。

## 16. 质量指标

优先关注：

1. 证据覆盖率：有可定位来源的有效声明 / 全部有效声明。
2. 版本覆盖率：带版本、哈希、提交或时间戳的来源 / 全部来源。
3. L2/L3 来源完整率：目标 100%。
4. 高风险知识验证率：目标 100%。
5. 项目事实误入 global 的数量：目标 0。
6. AI 自引用证据闭环数量：目标 0。
7. 断链和失效 canonical 路径数量：目标 0。
8. stale 条目比例和平均处置时间。
9. 冲突从发现到裁决的时间。
10. 候选→L2 的升格率与被拒原因。
11. 跨项目候选在目标项目完成验证的比例。
12. 人工审核每个升格条目的时间成本。
13. 固定工程问题集上的检索正确率和引用完整率。
14. 有效增长率：新增 L2/L3 声明数，而不是 Markdown 页数。

## 17. 主要反模式

- 把整个资料目录复制进 Vault 后称为“知识库”。
- 把 tmp、缓存、截图和中间产物当成知识。
- 把已有阅读笔记或 LLM 摘要当作原始事实。
- 同一内容在项目 KB、Obsidian 和 AI_Global_Assistant 三处分别维护。
- 因为知识达到 L2/L3，就把工程知识正文搬进 AI_Global_Assistant。
- 每次聊天都自动生成一篇笔记。
- 整页标 L3，但页面中混有推测和无来源建议。
- 新来源出现后直接覆盖旧结论，不保留冲突和适用范围。
- 为了“纯洁”静默删除被推翻知识，导致失效原因和反例不可追溯。
- 仅因为方法在 V500E 有效，就假定在 volant_XJ 有效，反之亦然。
- 用文件夹和标签替代真正的权限隔离。
- 自动判定脱敏完成，或自动发布跨项目结论。
- 让 AI 自行修改治理 Schema。
- 一开始就引入复杂 RAG、向量数据库或全自动定时写入。
- 用笔记数量、字数、链接数和图谱密度作为成功指标。

## 19. 标准提示词

### 单源摄入

~~~text
请按知识库 Ingest 流程处理这个来源。先判断权限、来源类型、项目归属和是否重复；只生成单源证据卡与知识增量提案，不直接升格。列出原文依据、假设、适用边界、冲突和待确认问题。若本任务已明确授权单源写入，可直接新建 L0/L1 并机械更新 index/log；否则先给出草案。修改已有正文、批量写入、合并或升格前必须先给出 diff 或变更清单并取得批准。
~~~

### 倾转旋翼文献

~~~text
使用 flight-literature-reader 三遍阅读法处理这篇文献。不要逐段翻译。先判断价值，再提取问题、输入输出、关键公式、假设、验证、工程价值和复现难点。单源证据与跨文献综合分开，文中未说明的内容明确标注。
~~~

### 查询与回写

~~~text
先读 index 和相关 canonical 页面，再回到必要原始来源回答。回答后先输出 ΔK route：no-change / project-only / obs-candidate / global-config-candidate；若不是 no-change，再输出 delta_operation：create / update / contradict / supersede / question。只有同时满足新意、可复用、有证据、范围明确、非重复时，才建议写回候选层。
~~~

### 跨项目迁移

~~~text
把该方法从来源项目整理为跨项目候选。不得复制参数、接口、模型结构、日志结论或受控资料。依次给出：来源项目已确认事实、抽象方法、脱敏说明、适用前提、不适用场景、目标项目验证计划、失败判据，以及 G0–G5 的确认人、时间、结论、产物路径和驳回原因。写入任一项目 KB 前需取得该项目的明确修改授权，并执行对应 kb-sync。
~~~

### 知识库 Lint

~~~text
只读检查本次范围内的知识库健康度：断链、孤儿、重复、无来源声明、AI 自引用、陈旧、冲突、项目泄漏、术语/符号不一致、待复核和已废弃仍被引用。先输出问题清单和建议修复，不自动改写语义内容。
~~~

## 20. 验收标准

最小可运行系统完成时，应满足：

- 每个知识对象有唯一 canonical 位置。
- 所有 L2/L3 结论有来源、适用范围和验证记录。
- 项目事实只保存在对应项目。
- 跨项目候选经过抽象、脱敏、来源项目复核和目标项目验证。
- 用户不需要手工复制项目 Markdown；每次项目任务结束均有四路由结果。
- 通用 L0–L3 工程知识正文位于 Obsidian，AI_Global_Assistant 只保存治理、配置和知识路由。
- 过期、冲突、已替代、已废弃和复核到期知识不会进入默认回答。
- 被推翻知识保留原因、证据、责任人和替代路径。
- 倾转旋翼原始 PDF、既有阅读笔记和方法论页面被分成不同来源等级。
- tmp 和过程缓存没有进入知识层。
- index 能找到全部非 deprecated 的 canonical 页面，并能从 pointer 追到新 canonical。
- log 能重建主要知识变更时间线。
- 默认工程答案只使用满足第 5.2 节唯一检索判据的知识；stale、conflicted、superseded 或 `review_status=deprecated` 的页面不会被当作默认结论。
- 高风险 L3 均有可复现验证产物、明确版本/工况和责任人批准。
- 删除、合并、跨项目发布和 Schema 修改都有人审记录。
- FlightControlKnowledgeableBase 保持完全未接入。
